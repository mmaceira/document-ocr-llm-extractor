# Statistics Graphs Documentation

This document explains each graph generated by the `generate_statistics.py` script. All graphs are saved in `outputs/{ocr-engine}/statistics/plots/`.

## Overview

The statistics generation script creates visualizations to help analyze the performance of the document extraction pipeline. Graphs are organized into several categories:

1. **Dimensional Analysis** - Bar charts and heatmaps showing performance across different dimensions
2. **Field-Level Analysis** - Detailed breakdowns of extraction accuracy per field
3. **Line-Item Analysis** - Performance metrics for list/array fields
4. **OCR Analysis** - Character and word error rate distributions
5. **Error Analysis** - Pareto charts identifying most common error types

---

## Dimensional Analysis Graphs

### 1. `extraction_by_doc_type.png`

**Type:** Stacked Bar Chart

**Description:** Shows field extraction percentages broken down by document type (deliverynote, bank, payroll). Each bar is divided into four segments:
- **Green (Exact Match):** Fields extracted perfectly
- **Orange (Minor Error):** Fields with small discrepancies (e.g., formatting differences)
- **Red (Major Error):** Fields with significant errors or wrong values
- **Gray (Not Extracted):** Fields that were not extracted at all

**Use Case:** Compare extraction performance across different document types to identify which types need improvement.

**Interpretation:** Higher green segments indicate better performance. If one document type has significantly more red or gray segments, it may need prompt tuning or model adjustments.

---

### 2. `extraction_by_language.png`

**Type:** Stacked Bar Chart

**Description:** Shows field extraction percentages broken down by language (es, en, ca). Uses the same color coding as the document type chart.

**Use Case:** Identify if extraction performance varies by language, which can indicate language-specific issues in prompts or OCR.

**Interpretation:** If one language performs significantly worse, consider:
- Language-specific prompt adjustments
- OCR language configuration
- Character encoding issues

---

### 3. `extraction_by_quality.png`

**Type:** Stacked Bar Chart

**Description:** Shows field extraction percentages broken down by **JPEG image quality levels** and PDF files. The x-axis is sorted from lowest to highest quality:
- **Low (JPG 10):** Lowest quality JPEG (high compression, more artifacts)
- **Medium (JPG 40):** Medium quality JPEG (moderate compression)
- **Good (JPG 90):** High quality JPEG (minimal compression)
- **Best (PDF):** Original PDF documents (no compression, best quality)

**Use Case:**
- Understand how JPEG compression quality affects extraction accuracy
- Lower quality images typically have more compression artifacts, which can lead to OCR errors and worse extraction performance
- Compare extraction performance between high-quality images, low-quality images, and original PDFs
- Determine if image preprocessing or quality enhancement is needed for low-quality inputs

**Interpretation:** You should see a trend where higher quality inputs (PDF, JPG 90) perform better than lower quality (JPG 10, JPG 40). If quality doesn't affect performance, OCR may be robust, or the bottleneck may be elsewhere (e.g., LLM extraction).

---

### 4. `extraction_by_file_type.png`

**Type:** Stacked Bar Chart

**Description:** Shows field extraction percentages broken down by file type (pdf, jpg). Compares performance between PDF documents and JPEG images.

**Use Case:** Determine if there's a performance difference between PDFs and images, which can help decide preprocessing strategies.

**Interpretation:** PDFs often perform better because they contain text directly (no OCR needed), while JPGs require OCR which can introduce errors. If the difference is large, consider using PDFs when possible or improving OCR preprocessing.

---

### 5. `heatmap_doc_type_quality.png`

**Type:** Heatmap

**Description:** Two-dimensional heatmap showing exact match percentages across document types (rows) and quality levels (columns). Warmer colors (yellow/orange/red) indicate higher accuracy, cooler colors indicate lower accuracy. The quality axis is sorted from lowest to highest: Low (JPG 10), Medium (JPG 40), Good (JPG 90), Best (PDF).

**Use Case:** Identify specific combinations of document type and quality that perform poorly, enabling targeted improvements.

**Interpretation:** Look for dark cells (low accuracy) to identify problematic combinations. For example, if "bank" documents with "JPG 10" quality show low accuracy, you may need to improve OCR preprocessing for low-quality bank statements.

---

### 6. `heatmap_doc_type_language.png`

**Type:** Heatmap

**Description:** Two-dimensional heatmap showing exact match percentages across document types (rows) and languages (columns). Warmer colors indicate higher accuracy.

**Use Case:** Identify language-specific issues for particular document types, which may require language-specific prompt tuning.

**Interpretation:** Dark cells indicate problematic language-document type combinations. This can reveal if certain languages need special handling or if prompts need language-specific adjustments.

## Field-Level Analysis Graphs

### 7. `per_field_accuracy_{doc_type}.png`

**Type:** Stacked Bar Chart

**Description:** Shows extraction accuracy for each individual field in a specific document type. Each field has a bar divided into the same four categories (exact match, minor error, major error, not extracted).

**Use Case:**
- Identify which fields are most problematic
- Prioritize improvements for specific fields
- Understand if certain fields are consistently harder to extract

**Example:** `per_field_accuracy_bank.png` shows accuracy for fields like `banco`, `titular`, `iban`, `lineas`, etc.

**Interpretation:** Fields with high gray (not extracted) or red (major error) segments need attention. Consider:
- Adding examples in prompts for difficult fields
- Adjusting field descriptions in the schema
- Checking if field names match document terminology

---

### 8. `per_field_f1_ci_{doc_type}.png`

**Type:** Bar Chart with Error Bars

**Description:** Shows token-level F1 scores for each field in a document type, with 95% confidence intervals calculated via bootstrap resampling. F1 score measures the harmonic mean of precision and recall at the token level, providing a more nuanced view than exact match.

**Use Case:**
- Understand partial matches (e.g., "Bank of America" vs "Bank of America Inc.")
- Identify fields with high variance in extraction quality
- Compare fields using a more granular metric than exact match

**Note:** Error bars show the uncertainty in the F1 estimate. Wider bars indicate more variability in extraction quality.

**Interpretation:**
- F1 > 0.9: Excellent extraction
- F1 0.7-0.9: Good extraction with minor issues
- F1 < 0.7: Needs improvement
- Wide error bars: Inconsistent extraction quality

## Line-Item Analysis Graphs

### 9. `line_item_recall_{doc_type}.png`

**Type:** Line Plot with Error Bars

**Description:** Shows how line-item recall varies with the number of items in the ground truth list. Data is binned by list length (rounded to nearest 5), and each point shows the mean recall with standard deviation error bars.

**Use Case:**
- Understand if extraction degrades as lists get longer
- Identify optimal list lengths for best performance
- Detect if there are issues with extracting large tables or lists

**Note:** This graph focuses on list/array fields like:
- `productos` (deliverynote) - product lines
- `lineas` (bank statements) - transaction lines
- `devengos` and `deducciones` (payroll) - earnings and deductions

**Interpretation:**
- If recall decreases as list length increases, the model may struggle with longer lists
- Consider chunking or splitting very long lists
- Check if the text limit is cutting off important list items

## OCR Analysis Graphs

### 10. `ocr_histograms.png`

**Type:** Dual Histogram

**Description:** Two-panel histogram showing the distribution of:
- **Left panel:** Character Error Rate (CER) - percentage of characters that differ between OCR output and ground truth
- **Right panel:** Word Error Rate (WER) - percentage of words that differ

Lower values indicate better OCR accuracy. The mean value is displayed in the title.

**Use Case:**
- Assess overall OCR quality
- Identify if OCR errors are a major source of extraction problems
- Compare OCR engines (when running with different `--ocr-engine` options)

**Interpretation:**
- **CER < 5%:** Excellent OCR - extraction errors likely due to LLM, not OCR
- **CER 5-10%:** Good OCR - minor OCR errors may affect extraction
- **CER > 10%:** Poor OCR - consider improving OCR preprocessing or using a different engine

**Note:** If OCR quality is poor, extraction accuracy will be limited regardless of LLM performance.

## Error Analysis Graphs

### 11. `error_pareto.png`

**Type:** Pareto Chart

**Description:** Shows the top 10 most common error types. The chart has two components:
- **Red bars:** Count of each error type
- **Blue line:** Cumulative percentage (shows how much of total errors are covered by the top N types)

**Use Case:**
- Identify the most frequent error types to prioritize fixes
- Apply the 80/20 rule: focus on the few error types that cause most problems
- Track improvements over time by comparing error distributions

**Common Error Types:**
- `wrong_value`: Extracted value is incorrect
- `format_mismatch`: Value is correct but formatted differently
- `not_extracted`: Field was not found
- `type_mismatch`: Value type doesn't match expected type
- `date_parsing_error`: Date field couldn't be parsed correctly

**Interpretation:**
- Focus on fixing the top 2-3 error types (they likely account for 60-80% of all errors)
- If `not_extracted` is high, improve prompts or field descriptions
- If `format_mismatch` is high, consider normalizing outputs or adjusting comparison logic

## Understanding the Metrics

### Exact Match
A field is considered an exact match when the extracted value exactly matches the ground truth value (after normalization). This is the strictest metric.

### Minor Error
Small discrepancies that don't significantly affect usability:
- Formatting differences (e.g., "1,234.56" vs "1234.56")
- Case differences (e.g., "Bank" vs "bank")
- Whitespace differences
- Minor punctuation differences

### Major Error
Significant discrepancies:
- Wrong values (e.g., extracted "Bank A" when ground truth is "Bank B")
- Missing required information
- Type mismatches
- Completely incorrect extractions

### Not Extracted
The field was not found or extracted at all. This could indicate:
- Field not present in the document
- Field name mismatch
- Prompt doesn't cover this field
- LLM failed to identify the field

### Token-Level F1
A more granular metric that measures partial matches. For example:
- Ground truth: "Bank of America"
- Extracted: "Bank of America Inc."
- Exact match: No
- Token F1: High (most tokens match)

This metric is useful for understanding near-misses and partial extractions. It's calculated by:
1. Tokenizing both strings
2. Computing precision and recall at the token level
3. Taking the harmonic mean: F1 = 2 × (precision × recall) / (precision + recall)

## Tips for Analysis

1. **Start with dimensional analysis** to identify broad patterns (which document types, languages, or qualities perform worst)

2. **Drill down to field-level** to find specific problematic fields

3. **Check OCR histograms** to see if OCR quality is a limiting factor - if CER > 10%, improve OCR before optimizing LLM

4. **Use error Pareto** to prioritize fixes based on frequency - focus on top 2-3 error types

5. **Compare across OCR engines** by running statistics for different `--ocr-engine` values and comparing the same graphs

6. **Track over time** by saving statistics from different runs and comparing trends

7. **Quality vs Performance:** If quality doesn't affect performance much, the bottleneck may be in LLM extraction rather than OCR

8. **Field-specific issues:** If one field consistently fails, check if it's mentioned in prompts and if the field name matches document terminology

## Generating Statistics

To generate all statistics and graphs:

```bash
python tools/generate_statistics.py --ocr-engine rapidocr
```

This will create all graphs in `outputs/rapidocr/statistics/plots/`.

To compare different OCR engines:

```bash
python tools/generate_statistics.py --ocr-engine rapidocr
python tools/generate_statistics.py --ocr-engine tesseract
python tools/generate_statistics.py --ocr-engine docling
```

Then compare the same graph files across different OCR engine directories.

## Graph File Naming Convention

All graphs follow a consistent naming pattern:
- `extraction_by_{dimension}.png` - Bar charts by dimension
- `heatmap_{dimension1}_{dimension2}.png` - Two-dimensional heatmaps
- `per_field_accuracy_{doc_type}.png` - Field-level accuracy per document type
- `per_field_f1_ci_{doc_type}.png` - Field-level F1 with confidence intervals
- `line_item_recall_{doc_type}.png` - Line-item recall analysis
- `ocr_histograms.png` - OCR error rate distributions
- `error_pareto.png` - Error type frequency analysis
